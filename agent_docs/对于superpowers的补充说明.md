# Superpowers Workflow Complexity Gating

本文件用于控制 superpowers 工作流的展开深度，避免简单任务被过度流程化。

核心原则只有一条：

**复杂度分层用于裁剪 workflow depth，不用于跳过 skill routing。**

也就是说：
- 先判断是否存在相关 superpowers skill；
- 若相关 skill 已触发，再根据任务复杂度决定流程展开到什么深度；
- 本文件用于控制 spec / plan / 分析 / 验证的强度，不用于否定 skill 本身的相关性。

## 优先级

若存在冲突，按以下顺序处理：

1. 用户的显式指令
2. 已触发的 superpowers skill
3. 本补充文档
4. 通用默认行为

本文件是对 superpowers 的兼容补充，不是替代它的第二套工作流。

## 总体策略

superpowers 的价值在于纪律、流程骨架和稳定性；它的代价是简单任务容易被复杂化，增加时间和 token 消耗。

因此：
- 对简单任务，保留判断与纪律，压缩流程展开；
- 对中等复杂度任务，保留骨架，裁剪不影响质量的步骤；
- 对高复杂度任务，保留完整流程，不为省事牺牲关键分析、设计和验证。

## 先决条件

在应用本文件之前，先完成以下判断：

- 当前任务是否存在相关 superpowers skill
- 该 skill 是 rigid 还是 flexible
- 当前任务的复杂度属于低 / 中 / 高

**不要因为任务看起来简单，就跳过 skill relevance 判断。**

## Rigid / Flexible 处理原则

### Rigid skills
若相关 skill 属于 rigid，默认不要因为“任务很小”就跳过其核心纪律。

可以压缩表达和文档产出，但不要擅自去掉这个 skill 的关键约束。  
低复杂度只能减少外显流程，不应破坏该 skill 的核心目的。

### Flexible skills
若相关 skill 属于 flexible，可以根据复杂度裁剪流程深度，只保留对当前任务真正有价值的部分。

## 复杂度判断

复杂度不是看“改动看起来小不小”，而是看总成本和出错后果。

综合判断以下信号：

- 目标是否清晰
- 改动落点是否明确
- 是否涉及多个模块或跨文件联动
- 是否存在明显方案分叉
- 是否有较高破坏风险
- 是否需要较长验证链路
- 是否需要先澄清问题本身，而不是直接实现

### 低复杂度
通常具备以下特征：

- 目标明确
- 落点清晰
- 改动范围小
- 无明显架构分叉
- 破坏风险低
- 验证方式直接且局部

处理方式：

- 不走 superpowers 的完整 spec → plan 流程
- 默认不写 spec
- 若确实需要计划，只采用最小充分计划
- 计划应短、小、直接服务于当前改动
- 避免为了“流程完整”而引入额外步骤
- 若判断该任务更适合先计划再做，直接向用户说明，并建议其开启 plan-only mode
- plan-only mode 视为 codex 自身的轻量计划模式，不等同于 superpowers 的完整规划链路

适配场景：

- 简单修复
- 局部小改
- 明确的小功能补丁
- 已有路径上的直接实现

### 中复杂度
通常具备以下特征：

- 目标基本明确
- 需要一定方案判断
- 可能跨多个文件或模块
- 存在一些实现分叉
- 需要计划，但不一定需要完整 spec
- 验证比低复杂度更重，但仍可局部控制

处理方式：

- 保留 superpowers 的流程骨架
- 可跳过 spec，直接写 plan
- plan 详略自行控制，以能支撑高质量实施为准
- 允许省略不影响结果质量的步骤
- 保留关键分析、关键验证和关键决策记录
- 不为了形式完整而补齐无实际价值的流程文档

适配场景：

- 中等规模改动
- 有一定设计判断的实现
- 涉及少量重构或多个落点的修改

### 高复杂度
通常具备以下特征：

- 问题本身还不够稳定
- 存在明显架构分叉
- 影响面较广
- 需要跨模块或系统级协调
- 验证链路较长
- 错误代价较高
- 若流程压缩，容易造成返工或错误设计

处理方式：

- 默认采用 superpowers 完整流程
- 不为节省时间或 token 而省略关键分析、设计、验证步骤
- spec、plan、验证强度按完整工作流执行
- 优先保证判断质量和实现稳定性

适配场景：

- 大改动
- 架构级调整
- 高风险问题
- 多阶段任务
- 问题定义本身仍需收敛的任务

## 裁剪原则

允许裁剪的是：
- spec
- plan 的详略
- 中间文档产出
- 不影响质量的外显流程步骤
- 过重的验证展示

不应轻易裁剪的是：
- skill relevance 判断
- rigid skill 的核心纪律
- 会影响设计正确性的关键分析
- 会影响稳定性的关键验证
- 对破坏风险的识别

## 反滥用约束

复杂度分层不能被当作偷懒借口。

以下理由不能单独作为降级依据：
- “这个看起来很简单”
- “我先直接改了再说”
- “先看代码，不急着走 skill”
- “完整流程太麻烦”
- “也许不用那么严格”

只有当任务特征本身支持更轻的流程时，才允许降级。

若不确定是低复杂度还是中复杂度，优先选中复杂度。  
若不确定是中复杂度还是高复杂度，取决于错误代价：  
- 若判断失误的代价明显高，按高复杂度处理；
- 否则按中复杂度处理。

## 输出要求

除非用户明确要求，不要把内部复杂度分层、skill routing 或裁剪过程表演出来。

只有在以下情况才显式说明：
- 需要建议用户开启 plan-only mode
- 需要解释为什么这次保留了完整流程
- 需要说明为何跳过某些文档化步骤不会影响质量

默认只体现结果，不表演路由。

## 一句话总结

先尊重 skill routing，再按复杂度裁剪 workflow depth。  
简单任务不做重流程，中等任务保留骨架，高复杂度任务保留完整纪律。  
省的是无价值流程，不省会影响判断质量和实现稳定性的部分。
